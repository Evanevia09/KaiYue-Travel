## 2. What this is, and what it is not

**Not a broken admin app, and not a missing login route.** On `admin-staging.kaiyuemacau.com`, `/login` returns the sign-in page and `/admin` redirects unauthenticated users to `/login`. Those responses are uncached (no `cf-cache-status`). Host isolation works: the same `/login` and `/admin` paths on `staging.kaiyuemacau.com` and on `*.workers.dev` are 403 `no-store`.

**Not a zone Cache Rule or Page Rule.** Zone `kaiyuemacau.com` (`fb84210cb8175ff4412b444805e1a6a5`, Free Website, development mode off, cache_level `aggressive`) has zero Page Rules. The `http_request_cache_settings` entrypoint returns 404 “could not find entrypoint ruleset” — there is no Cache Ruleset configured. Managed firewall/normalization rulesets only.

**The defect is specifically admin-staging `/` (and `/index.html`) serving the public marketing homepage.** That body is byte-identical (`9831b439a1ed…`, 31145 bytes, title “Private chauffeur across the Greater Bay Area · Kai Yue Travel”) to public staging `/` and to workers.dev `/`. All of those are `cf-cache-status: HIT` with `Cache-Control: public, max-age=0, must-revalidate`.

**This is Workers / asset-edge cache behavior, not only a custom-hostname zone cache.** workers.dev is not on a zone route or Workers custom domain record; it still HITs the same HTML. Staging and admin-staging both use Workers custom domains to the same script `kaiyue-travel-staging` (see §3). There is no `Vary: Host`, so a cacheable `/` HTML object is reused across those hostnames.

**A client cache-bust is not an origin miss.** Unique query strings and `Cache-Control: no-cache` / `Pragma: no-cache` request headers still returned HIT and the same hash. Cloudflare / Workers asset cache does not honor client no-cache, and the cache key here is not distinguishing the query string. Therefore this probe **cannot** prove what the Worker would return on a true cache miss for admin-staging `/`. Two remaining possibilities, both consistent with the HIT evidence:

1. Stale or host-agnostic cached prerendered `index.html` is served at `/` and the admin-host root handler never sees the request (or its response is overwritten by the cached asset). Live metadata has `raw_run_worker_first`: `/*`, `!/_astro/*`, `!/images/*`, `!/favicon.ico`, so `/` is supposed to run the Worker first. A host-agnostic HTML cache of `/` can still defeat that for subsequent HITs.
2. The Worker itself returns the marketing homepage at `/` even on the admin host, and that response is then cached as `public`. Version 12 was annotated `admin-host root sign-in`; smoke still refuses to assert admin `/`. If (2) is true, a purge alone will not last.

Because there is no `Age` header, the cached object also cannot be dated relative to the 16:37 Asia/Macau activation. A prior cache-purge permission remains pending; this investigation did not purge and did not retry that permission.
